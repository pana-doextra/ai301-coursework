# Rubric: is this pull request ready to submit?

Compare actual artifacts with the accepted plan plus declared deviations.
Use only stated repo requirements. Terseness, missing optional headings,
and lack of a policy the repo never adopted are not failures.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | Plan context's scope, exclusions, approach, and deviation notes alongside every diff file and behavioral hunk; live: `plan.md` and `git diff main...HEAD`. | The diff implements the bounded planned behavior; each material addition, omission, or replacement is accounted for in deviations and explained by the same issue. A disclosed narrower delivery can pass when its boundary and remaining work are explicit. Silent extra work, missing planned behavior without a note, and unrelated rewrites fail. Naming an unrelated change does not bring it into scope. | required |
| claims-match-artifacts | Title and description's delivery and fidelity claims alongside the diff, commits, and test evidence. | Load-bearing claims match the actual approach, scope, observations, and limitations. Reject exact-plan claims contradicted by changed hunks, unsupported platform or check-success claims, and an unqualified complete fix when only a subset is delivered. Honest limitations and identified hypotheses pass. Judge material delivery claims rather than incidental test-case labels or exact diagnostic wording. Frozen diffs are excerpts: do not infer a contradiction from unseen unchanged callers, helpers, tests, or error formatting. A concrete contradictory artifact is needed; do not speculate about omitted implementation. | required |
| behavior-evidence | Plan's test plan and accepted repro's inputs, controls, and distinct failure modes alongside candidate test evidence. | Evidence identifies a run or concrete artifact and an observable branch result distinguishing fixed from not fixed for the delivered behavior, against established before and expected after. Each distinct planned failure mode and relevant planned control is covered or explicitly disclosed as untested with a reason and bounded claim. Distinct means different triggers or outcomes the test plan specifically promises to exercise, not every sibling method receiving the same fix. A representative repro plus an executed regression assertion and suite can verify one shared mechanism without separate transcripts for identical sibling changes. Silent omission of a separately named failure mode fails even if another passes. Candid partial verification can pass if decisive evidence for the delivered claim remains; disclosure alone with no decisive observation cannot. Generic tests-pass assertions, added test files, or expectations without run results are insufficient. | required |
| repo-checks-evidence | Repo facts' requested checks and plan's suite commands alongside recorded outcomes; live: template, `docs/CONTRIBUTING.md`, and `test_evidence.md`. | Applicable repo checks or the planned suite have recorded runs and outcomes; failures include their error and reason rather than being hidden behind green boxes. An explained unavailable check is allowed if its limitation is disclosed and remaining evidence verifies the bounded change, unless stated policy makes it a non-waivable gate at this stage. No checks or suite evidence at all fails. Do not require every suite to succeed, invent commands, or require future CI on a draft. | required |
| reviewable-diff | All unified diff hunks and the commit list compared with the bounded fix. | A reviewer can isolate the fix without unrelated hunks or execution debris: no leftover debug output, abandoned/commented-out implementation, dead experiments, drive-by refactors, or irrelevant formatting churn. Necessary supporting tests/docs and coherent same-cause changes are allowed. No file, line, or commit-count threshold applies. | required |
| repo-standards | Repo-facts template asks and contributing rules alongside title, description, commits, and changed tests/docs; live also scope's house rules and issue thread. | Each applicable stated template request receives substantive content or an explained N/A; required tests/docs/changelog and naming conventions are honored. Maintainer direction is followed or departure is acknowledged with a reason without bypassing a binding requirement. Do not invent templates, exact headings, or unstated changelog obligations. Live Path Review drafts use every template section, keep future CI unticked, and explain an empty integration suite honestly; inspect CI separately after opening. | required |
| disclosure-compliant | Explicit AI-use policy and candidate disclosure; live: policy docs and Notes for Reviewers. | Where disclosure is explicitly required, the description identifies actual AI use, tool, and extent as requested. An explicit prohibition cannot be satisfied by disclosure. No stated disclosure policy means none is required in eval; AI mentions, responsibility language, and review concerns do not create one. Live Path Review coursework always includes the course-required account of AI use in Notes for Reviewers. | required |
| regression-guard | Changed automated assertions read against the reproduced behavior and recorded runs. | A durable test asserts the delivered behavior and is shown running; seeded tests covering the fix lose their issue-specific strict xfail markers and matching suppressions. Manual-only verification can still be ready; this preference never rejects. Explicit repo test requirements are assessed by repo-standards. | preferred |

## Verdict rule

Accept if and only if every `required` check is `pass`. Any required
`fail` or `unclear` produces `reject`; retain `unclear` as the reported
grade so missing evidence stays visible. Preferred grades are reported
but never counted. Do not average, vote, or stop on the first failure.
Honest shortfalls pass only within the relevant row's exception; they
do not override another required failure.
