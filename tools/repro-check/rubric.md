# Rubric: is this reproduction package ready to post?

Every check reads the package against the issue it belongs to. In eval mode
the bundle is the whole world: the `## Repo facts` block, the `## Issue`
section, `## Thread highlights`, `## Candidate claim comment`, and
`## Candidate repro report`. In live mode the same parts live where
`references/evidence-guide.md` says they do.

Grade the proof, never the shape. A terse transcript can be a complete
reproduction and a long headed report can be empty.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The environment record in the repro report — wherever it sits, prose or block, naming the platform, the version or code state, and how the software was obtained — read against the issue body's own version/OS lines and the fields named on the repo-facts `bug reports:` template line. | The report names **(a)** the OS or platform it ran on, **(b)** the version, release, tag, or commit of the software under test, and **(c)** every further dimension the issue itself makes decisive for the behavior: the build profile when the issue's outcome differs between debug and release, the driver or backend when the issue is specific to one, the shell or terminal when the bug is a terminal-rendering bug, the install method when the issue turns on packaging. If the environment tested differs from the one the issue targets — different version, different OS, different install route — the report must **say so in words**; a silent deviation fails even when the result looks right. A convincing artifact never substitutes for the record: a reader who cannot tell what was run cannot re-run it. | required |
| steps-followable | The reproduction steps in the repro report: the commands, keystrokes, or UI actions, plus the starting state they assume. Read against the steps the issue gives, if it gives any. | A stranger holding the recorded environment could get from a stated starting state to the trigger without inventing anything. The starting state is given or trivially implied (`git init -q t && cd t && touch new.txt` states it; "in a repo" does not, when which repo decides the outcome), and the exact command or action that triggers the behavior appears verbatim. Steps may be **shorter** than the issue's own where the report shows they reach the same trigger. Fails when a step the issue makes decisive is omitted, or when the trigger is described only in prose ("I searched for something that wasn't there") on an issue whose behavior depends on the specific input. Terseness is not a failure, and a transcript that is itself the steps passes. | required |
| artifact-shown | Output excerpts, command transcripts, logs, tracebacks, exit codes, screenshots, or state dumps in the repro report — the parts of it a machine produced rather than the author. | The report carries at least one artifact produced by the run. An assertion about what happened is not an artifact, however detailed, confident, or well organised. Absence of output **can** be the artifact when the bug is a silent no-op, provided the report shows the command that produced nothing **and** a state check proving the expected effect is missing (an empty `git stash list` next to a still-untracked `?? new.txt`). Me-too statements, frequency claims, and other people's experience ("everyone I know has this") are never artifacts. | required |
| behavior-matches-issue | The artifact from `artifact-shown`, read line by line against the specific failure the issue describes: its error text, exception or panic message, exit code, stack frames, or described visible behavior. Also the input and invocation inside the transcript, read against the input and invocation the issue names. | The artifact shows **the issue's own failure signature**, not merely that something went wrong. Compare the identifying detail: a `panic: not a string` is not shown by an `Error: unable to parse hcl ... Missing key/value separator`; a capacity-overflow crash exiting 101 is not shown by an argument-validation error exiting 1. Check the transcript's own input too — a transcript that writes `{ 1: {} }` where the issue wrote `{ 1 = {} }` is reproducing a different bug, and so is one that runs a prefix range where the issue specified an offset-from-end. **An honest cannot-reproduce passes this check**: a report that ran the issue's trigger faithfully in a recorded environment, observed the behavior not occurring, and says plainly that it did not reproduce is a correct and postable result. What fails is a mismatch narrated as a match. | required |
| honest-narration | The report's conclusion, analysis, and summary sentences, read against what its own artifacts actually show; plus any statement in the claim comment about what has already been established. | Every claim of fact carrying the argument is backed by something in the package. Fails on: narrating an artifact as confirming the issue when it shows something else; unverifiable scale or frequency offered as evidence ("all my machines", "every single day", "everyone I know"); asserted extra environments whose output never appears while the conclusion leans on them ("also confirmed on 4.53.2 to match the reporter"); unshown repeat runs offered as what makes a claim true, where the package's own artifacts never show the behavior ("ran it ten times with identical results", under a bug the report never once exhibits); and a diagnosis of the cause stated as an established finding rather than a hypothesis. A hedge marked as a hedge passes — "I suspect", "this may be", "my guess is" — and so does an intended investigation direction. A repeat count that reports the shown artifact's own outcome holding steady is **not** this failure — it inflates nothing, and a cannot-reproduce report saying how many attempts it made is being precise about a negative, not leaning on hidden proof. Nor is a single control run inside the already-recorded environment, reported in prose as a plain observation of what it printed: it claims no environment and no scale the package has not already established, and its missing transcript is a matter for `control-or-contrast`, not for honesty. Confidence language on its own is not the failure; confidence exceeding the package's own evidence is. | required |
| claim-specific-and-modest | The `## Candidate claim comment`, read against the issue's title and body. (Claim-side: gradeable on a claim-only draft.) | The claim shows its writer read **this** issue — it restates the issue's actual subject in the writer's own words, or names a specific behavior, symptom, file, or code path drawn from it — **and** it promises only investigation. A stated intended direction passes ("plan: find where the stash-name prompt decides to appear", "I'll offer independent testing across build profiles"). What fails is committing to a delivery: promising a fix, a pull request, or a date as a commitment rather than an intention; or a contentless reaction — a bare "+1", "same here", "claiming this" — that would read identically under any issue in the tracker. Emotional register, emoji, exclamation marks, and length are not graded: a terse specific claim passes and a long warm boilerplate one fails. | required |
| conventions-and-disclosure | The `contribution policy` line of the repo-facts block, plus its `bug reports:` template line. Live: `CONTRIBUTING.md` in the repo root or `.github/`, any `AI_POLICY.md`, the docs those link to, and the issue template. Read against **both** posted comments. (Claim-side: gradeable on a claim-only draft.) | If the repo's stated policy **requires disclosing AI assistance** on contributions or comments, at least one of the two comments says plainly that AI assistance was used; silence where disclosure is required fails, however strong the proof is. If the policy states no disclosure requirement, this check passes with no disclosure present — and these are **not** requirements: permissive-with-responsibility language, a maintainer's note that review time is scarce or that AI-generated PRs are hard to assess, a human-review or testing obligation, a rule that comments to maintainers be written by a human in their own words rather than pasted from a model, a standard contribution guide, or no AI policy at all. Do not infer a requirement from a maintainer merely mentioning AI. A policy banning AI-assisted contribution outright also fails here: our workflow cannot honestly comply — but read what the ban covers. A rule against AI-*written comment text*, or against AI-generated PRs with no human in the loop, is not a ban on AI-assisted contribution: a comment the contributor wrote in their own voice already complies with it, and owes no disclosure. | required |
| control-or-contrast | A second run in the repro report alongside the failing one: a near-miss input, an unaffected version, a pre-condition run, or the same command shifted off the trigger. | The package isolates the trigger by showing something that does **not** fail next to the thing that does — a scan shifted away from the boundary completing normally, a minus-replace run behaving correctly. This is what separates "I saw a crash" from "I found the edge". Its absence never rejects a package. | preferred |
| tested-on-current | The version in the report's environment record, read against the `latest release` line in the repo-facts block and the version the issue was filed from. | The reproduction ran against the current release or repository tip rather than only the older version the issue was filed from, so the report tells a maintainer the bug is still live. | preferred |

## Verdict rule

**Accept if and only if every `required` check grades `pass`.** A single
required `fail` rejects the package. The remaining required checks are still
graded and reported, so the summary shows every reason it was held, not just
the first one found.

`unclear` on a required check counts as **fail**. Proof a reader cannot
verify from the package is proof that is not ready to post; an environment,
a trigger, or a disclosure obligation that cannot be established from the
evidence in front of you is not established.

`preferred` checks never change the verdict. They are graded and reported,
and on an accepted package they say how strong it is — an accepted package
carrying a control run against the current release is a better comment than
an accepted package without one, and both are postable.

**Claim-only drafts** (live mode, before the repro comment exists) are
graded on `claim-specific-and-modest` and `conventions-and-disclosure`
alone. The other checks report `unclear` with evidence `not yet applicable:
claim-only draft` and are excluded from the verdict rule rather than counted
as fails; the verdict then answers only whether the claim comment is ready
to post.
